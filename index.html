1. Containers (Docker e Kubernetes)

Visão geral: é o tema mais “técnico” do bloco e cai muito em comparação com máquinas virtuais e em componentes do Kubernetes.

Teoria em camadas

Analogia: a VM é uma casa completa, com fundação e infraestrutura próprias. O container é um apartamento: cada um é isolado, mas todos dividem a estrutura do prédio (o kernel do sistema operacional).

Máquina VirtualContainer
VirtualizaO hardware (hypervisor)O sistema operacional
Sistema operacionalSO convidado completoCompartilha o kernel do host
Peso e inícioGBs, minutosMBs, segundos
IsolamentoMais forteMais leve (namespaces e cgroups)
  • Namespaces isolam (processos, rede, pontos de montagem). cgroups limitam (CPU e memória). Maceta: Namespace = “o que eu enxergo”; cgroup = “quanto eu posso gastar”.
  • Imagem: modelo somente leitura, feito em camadas, criado a partir de um Dockerfile. Container: imagem em execução, com uma camada de escrita por cima.
  • Registry (ex.: Docker Hub) guarda imagens. Comandos: build cria a imagem, run executa, push/pull enviam e baixam.
  • Dados que precisam sobreviver ao container ficam em volumes, pois a camada de escrita some junto com ele.

Kubernetes: o orquestrador

Docker roda um container. Kubernetes (K8s) gerencia centenas: escala, reinicia os que caem e distribui carga.

Control Plane (cérebro)Worker Node (músculo)
kube-apiserver: porta de entrada de tudo
etcd: banco chave-valor com o estado do cluster
scheduler: decide em qual nó o Pod roda
controller-manager: mantém o estado desejado		 kubelet: agente que executa os Pods no nó
kube-proxy: regras de rede
container runtime: containerd, CRI-O
  • Pod: menor unidade; um ou mais containers que dividem IP e volumes.
  • Deployment gerencia réplicas e atualizações (rolling update). Service dá IP e nome estáveis aos Pods. Ingress expõe HTTP/HTTPS externamente.
  • ConfigMap guarda configuração; Secret guarda dados sensíveis (em base64, que não é criptografia). Namespace divide o cluster logicamente.
  • StatefulSet é para aplicações com estado (bancos); DaemonSet roda um Pod em cada nó.
Maceta: API recebe → etcd guarda → Scheduler escolhe → kubelet executa. O que decide e guarda fica no Control Plane; quem executa fica no Worker.
Cai na prova assim:
  • “Containers possuem hypervisor e SO convidado próprios” → ERRADO. Compartilham o kernel do host.
  • “O etcd é executado nos Worker Nodes” → ERRADO. É do Control Plane.
  • “Secret criptografa os dados por padrão” → ERRADO. Só codifica em base64.
Resumo de 1 minutoContainer compartilha kernel; VM tem SO próprio. Imagem é somente leitura, container tem camada de escrita. K8s: Control Plane (apiserver, etcd, scheduler, controller-manager) e Worker (kubelet, kube-proxy, runtime). Pod é a menor unidade; Deployment escala; Service expõe.

Questões comentadas

Q1 (Certo/Errado): No Kubernetes, o kubelet é executado no Control Plane e decide em qual nó cada Pod será alocado.ERRADO. Quem decide o nó é o scheduler (Control Plane). O kubelet roda em cada Worker e executa os Pods designados.
Q2: Qual recurso do Linux limita o consumo de CPU e memória de um container? a) namespaces b) cgroups c) UnionFS d) etcdLetra b. cgroups limitam recursos; namespaces isolam; UnionFS forma as camadas da imagem; etcd é do Kubernetes.

2. DevOps e DevSecOps

Visão geral: cultura mais do que ferramenta. A banca cobra siglas (CI, CD) e a ideia de “Shift-Left”.

Teoria em camadas

DevOps une Desenvolvimento (quer mudar rápido) e Operações (quer estabilidade) para entregar software com frequência e qualidade. Pilares conhecidos como CALMS: Cultura, Automação, Lean, Medição, Sharing (compartilhamento).

SiglaO que é
CI Integração ContínuaDevs enviam código ao repositório várias vezes ao dia; cada envio dispara build e testes automáticos.
CD Entrega Contínua (Delivery)O código fica sempre pronto para produção, mas a liberação final é manual (aprovação humana).
CD Implantação Contínua (Deployment)Toda mudança aprovada nos testes vai para produção automaticamente, sem aprovação humana.
Maceta: Delivery = “posso publicar”. Deployment = “já publicou”.
  • Pipeline: esteira automática: código → build → testes → empacotamento → deploy.
  • IaC (Infraestrutura como Código): servidores e redes descritos em arquivos versionados. Ferramentas: Terraform (provisiona), Ansible (configura). Benefício: ambientes idênticos e repetíveis.
  • Monitoramento e feedback: logs, métricas e alertas (ex.: Prometheus, Grafana) fecham o ciclo.
  • Ferramentas de CI/CD comuns: Jenkins, GitLab CI, GitHub Actions.

DevSecOps

Segurança deixa de ser a “última fase” e entra desde o início: é o Shift-Left (deslocar a segurança para a esquerda da linha do tempo). Achar falha cedo custa muito menos.

TesteComo funciona
SASTAnalisa o código-fonte sem executar (“caixa-branca”).
DASTAtaca a aplicação em execução (“caixa-preta”).
SCAVerifica vulnerabilidades em bibliotecas e dependências de terceiros.
IASTCombina os dois: instrumenta a aplicação durante os testes.
Cai na prova assim:
  • “DevOps é um cargo/ferramenta específica” → ERRADO. É cultura e conjunto de práticas.
  • “Entrega contínua implanta automaticamente em produção” → ERRADO (isso é implantação contínua).
  • “SAST testa a aplicação em execução” → ERRADO. É o DAST.
Resumo de 1 minutoDevOps = cultura Dev + Ops. CI integra e testa; Delivery tem aprovação manual; Deployment é automático. IaC versiona infraestrutura. DevSecOps = segurança desde o início (Shift-Left): SAST (código), DAST (rodando), SCA (dependências).

Questões comentadas

Q1 (C/E): Em DevSecOps, o princípio Shift-Left propõe tratar a segurança somente após a implantação, em testes de penetração.ERRADO. É o contrário: antecipa a segurança para as fases iniciais.
Q2: A análise de vulnerabilidades em bibliotecas de terceiros é feita por: a) SAST b) DAST c) SCA d) IaCLetra c. SCA (Software Composition Analysis) examina dependências.

3. Padrões de Arquitetura de Software

Visão geral: a banca descreve um cenário e pede o nome do padrão. Decore a “ideia central” de cada um.

Atenção: padrão de arquitetura organiza o sistema inteiro (camadas, MVC). Padrão de projeto (GoF) resolve problema de código dentro de classes. Não confunda.

Monolito x Microsserviços

  • Microsserviços ganham: escalabilidade independente, deploys isolados, liberdade de tecnologia.
  • Microsserviços perdem: complexidade operacional, consistência de dados distribuída, latência de rede, mais monitoramento.
  • Microsserviços combinam bem com containers, Kubernetes e DevOps (tópicos 1 e 2).
Maceta MVC: Controller recebe o pedido do usuário, manda o Model trabalhar e escolhe qual View mostrar. Como um garçom (Controller) que leva o pedido à cozinha (Model) e entrega o prato (View).
Cai na prova assim:
  • “No MVC, a View acessa o banco diretamente” → ERRADO. Quem trata dados é o Model.
  • “Em microsserviços, todos os serviços compartilham obrigatoriamente o mesmo banco” → ERRADO. O ideal é cada serviço ter o seu.
  • “Microsserviços reduzem a complexidade operacional” → ERRADO. Aumentam.
Resumo de 1 minutoCamadas = níveis. MVC = Model, View, Controller. Monólito = um bloco; microsserviços = serviços pequenos e independentes. Eventos = assíncrono por filas. Hexagonal = núcleo protegido. CQRS = separa leitura de escrita.

Questões comentadas

Q1 (C/E): No padrão MVC, o Controller é responsável pela apresentação visual dos dados ao usuário.ERRADO. A apresentação é papel da View. O Controller interpreta a entrada e coordena Model e View.
Q2: Qual padrão separa as operações de leitura das de escrita em modelos distintos? a) Hexagonal b) CQRS c) Pipes and Filters d) CamadasLetra b. CQRS = Command Query Responsibility Segregation.

4. SOA, Web Services e REST

Visão geral: o foco é diferenciar SOAP de REST e conhecer verbos HTTP e códigos de status.

SOA

Arquitetura Orientada a Serviços: o sistema é montado a partir de serviços reutilizáveis, de baixo acoplamento e contratos bem definidos, que o negócio consome. Costuma usar um ESB (barramento de serviços) para integrar. Diferença para microsserviços: SOA é mais corporativa e centralizada; microsserviços são menores e descentralizados.

SOAP x REST

SOAPREST
NaturezaProtocoloEstilo arquitetural (Roy Fielding, 2000)
FormatoSomente XMLJSON, XML e outros
ContratoWSDL (descreve o serviço)Opcional (ex.: OpenAPI)
TransporteHTTP, SMTP e outrosHTTP
PesoMais pesado e rígidoMais leve e simples
  • SOAP: mensagem em um Envelope (Header + Body). UDDI é o diretório de serviços (hoje pouco usado).
  • Maceta: SOAP = “Simple Object Access Protocol”, mas na prática é o mais complexo. REST lembra “descanso”: simples.

As 6 restrições do REST

Cliente-servidor · Stateless (sem estado: cada requisição traz tudo o que o servidor precisa) · Cache · Interface uniforme · Sistema em camadas · Código sob demanda (opcional).

  • Tudo é um recurso, identificado por uma URI (ex.: /processos/10).
  • HATEOAS: a resposta traz links para as próximas ações possíveis.

Verbos HTTP

Idempotente: repetir a mesma chamada várias vezes produz o mesmo resultado final. Seguro: não altera dados.

Códigos de status

2xx sucesso (200 OK, 201 Created, 204 No Content) · 3xx redirecionamento · 4xx erro do cliente (400, 401 não autenticado, 403 proibido, 404 não encontrado) · 5xx erro do servidor (500, 503).

Maceta: 401 = “quem é você?” (falta autenticação). 403 = “sei quem é, mas não pode” (falta permissão).
Cai na prova assim:
  • “REST é um protocolo que utiliza exclusivamente XML” → ERRADO. É um estilo e aceita JSON.
  • “Na API REST o servidor guarda a sessão do cliente entre requisições” → ERRADO. É stateless.
  • “POST é idempotente” → ERRADO.
Resumo de 1 minutoSOA = serviços reutilizáveis e fracamente acoplados. SOAP = protocolo, XML, WSDL. REST = estilo, stateless, JSON, URIs e verbos HTTP. GET/PUT/DELETE são idempotentes; POST não. 4xx cliente, 5xx servidor.

Questões comentadas

Q1 (C/E): O WSDL é o documento que descreve a interface de um serviço SOAP.CERTO. WSDL (Web Services Description Language) descreve operações, mensagens e endereço.
Q2: Qual código HTTP indica que um recurso foi criado com sucesso? a) 200 b) 201 c) 204 d) 404Letra b. 201 Created, comum após um POST.

1. BI, Data Warehouse, ETL, OLAP e ERP

Visão geral: é a “cadeia” que leva o dado do sistema do dia a dia até o gráfico que o gestor usa para decidir.

Analogia: os sistemas operacionais são as cozinhas de vários restaurantes. O ETL é o caminhão que coleta e padroniza os ingredientes. O Data Warehouse é o grande armazém organizado. O OLAP é a vitrine para o gestor escolher como quer olhar. O BI é todo o processo.

  • BI (Business Intelligence): conjunto de técnicas e ferramentas que transformam dados em informação para apoiar decisões.
  • Data Warehouse (DW): repositório central, histórico e integrado, feito para análise. Segundo Inmon, é: orientado a assunto, integrado, não volátil (dado não é alterado ou apagado) e variante no tempo (guarda histórico).
  • Data Mart: fatia do DW voltada a um departamento (vendas, RH).
  • Inmon = top-down (primeiro o DW corporativo, depois os marts). Kimball = bottom-up (primeiro os marts, que formam o DW).
  • ETL: Extract (extrai das fontes) → Transform (limpa, padroniza, integra) → Load (carrega no DW). Os dados passam antes por uma staging area (área temporária). Em ELT, carrega primeiro e transforma depois.
OLTP (operacional)OLAP (analítico)
FocoTransações do dia a diaConsultas e análises
DadosAtuais, detalhadosHistóricos, resumidos
OperaçõesMuitas inserções e atualizaçõesMuita leitura
ModeloNormalizadoDimensional (desnormalizado)

Modelagem dimensional e OLAP

  • Tabela fato: guarda as medidas numéricas (valor da venda, quantidade). Dimensões: o contexto (tempo, produto, cliente, local).
  • Esquema estrela: fato no centro, dimensões desnormalizadas ao redor. Floco de neve (snowflake): dimensões normalizadas em várias tabelas.
  • Operações OLAP: drill-down (detalhar: ano → mês), roll-up (resumir: mês → ano), slice (fatiar uma dimensão), dice (cubo menor com várias dimensões), pivot (girar eixos).
  • MOLAP (cubo multidimensional, rápido), ROLAP (sobre banco relacional, escala melhor), HOLAP (híbrido).

ERP

Sistema integrado de gestão que reúne os módulos da empresa (financeiro, estoque, RH, compras) em uma única base de dados. Exemplos: SAP, TOTVS. Evita ilhas de informação. O ERP é uma fonte de dados para o DW, não um substituto dele.

Cai na prova assim:
  • “O DW é volátil: os dados são constantemente alterados” → ERRADO. É não volátil.
  • “Roll-up detalha os dados em níveis mais baixos” → ERRADO. Isso é drill-down.
  • “O DW é otimizado para transações OLTP” → ERRADO. É para análise (OLAP).
Resumo de 1 minutoETL alimenta o DW (assunto, integrado, não volátil, histórico). Data Mart = parte do DW. OLTP = operacional; OLAP = análise. Fato = medidas; dimensões = contexto. Drill-down detalha; roll-up resume. ERP = sistema integrado, base única.

Questões comentadas

Q1 (C/E): Na etapa Transform do ETL ocorrem limpeza e padronização dos dados antes da carga no DW.CERTO. É a etapa de tratamento e integração.
Q2: Qual operação OLAP sai de “vendas por ano” para “vendas por mês”? a) roll-up b) drill-down c) slice d) pivotLetra b. Descer em nível de detalhe = drill-down.

2. Conceitos Básicos e Arquitetura de Três Esquemas

Visão geral: base de tudo. A prova cobra as características do SGBD e as 3 camadas ANSI/SPARC.

  • Banco de dados (BD): coleção de dados relacionados. SGBD: software que cria e gerencia o BD (Oracle, PostgreSQL, MySQL, SQL Server). Sistema de BD = BD + SGBD + aplicações.
  • Características da abordagem de BD (comparada a arquivos soltos): autodescrição (guarda o catálogo), isolamento entre programas e dados (abstração), múltiplas visões e compartilhamento com transações multiusuário.
  • Vantagens: menos redundância, integridade, segurança, controle de acesso, backup e recuperação.

Arquitetura de três esquemas (ANSI/SPARC)

NívelO que descreveMaceta
Externo (visões)O que cada usuário ou aplicação enxerga“o que eu vejo”
Conceitual (lógico)Estrutura de todo o BD: tabelas, relacionamentos, restrições“o que existe”
Interno (físico)Armazenamento: arquivos, índices, caminhos de acesso“como é guardado”
  • Independência lógica: alterar o esquema conceitual sem mudar os esquemas externos/aplicações.
  • Independência física: alterar o esquema interno sem mudar o conceitual. Ex.: criar um índice, trocar o disco.

Linguagens e transações

  • DDL define estruturas; DML manipula dados; DCL controla permissões; TCL controla transações.
  • ACID: Atomicidade (tudo ou nada), Consistência (BD sai de um estado válido para outro válido), Isolamento (transações concorrentes não interferem), Durabilidade (o que foi confirmado persiste).
Cai na prova assim:
  • “Criar um índice exige alterar os programas de aplicação” → ERRADO. Isso é independência física.
  • “O esquema externo define como os dados são armazenados em disco” → ERRADO. Isso é o interno.
  • Trocar atomicidade por “isolamento” na definição de ACID é pegadinha comum.
Resumo de 1 minutoSGBD gerencia o BD. Três esquemas: externo (visões), conceitual (lógico), interno (físico). Independência lógica protege o externo; física protege o conceitual. ACID: Atomicidade, Consistência, Isolamento, Durabilidade.

Questões comentadas

Q1 (C/E): A independência física de dados permite alterar a organização dos arquivos sem afetar o esquema conceitual.CERTO. A mudança no nível interno não propaga para o conceitual.
Q2: A propriedade ACID que garante “ou executa tudo, ou nada” é: a) Consistência b) Isolamento c) Atomicidade d) DurabilidadeLetra c. Atomicidade.

3. Metadados de Arquivos

Visão geral: tema curto e objetivo. Quase sempre cai como “onde ficam os metadados” e “o que é autodescrição”.

Metadados são “dados sobre dados”. Analogia: num livro, o texto é o dado; a ficha catalográfica (autor, ano, editora) é o metadado.

  • Dicionário de Dados / Catálogo do sistema: conjunto de tabelas do próprio SGBD que guardam a descrição de tabelas, colunas, tipos, chaves, restrições, visões, índices e permissões.
  • Autodescrição: o SGBD guarda junto dos dados a descrição da própria estrutura. É uma característica que o diferencia do sistema de arquivos tradicional.
  • Information Schema: padrão ANSI SQL para consultar metadados.
  • Tipos: técnicos (tipo de dado, tamanho), de negócio (significado, regra) e operacionais (quando e quem alterou, volume).
  • Metadados de arquivo: nome, tamanho, datas de criação/modificação, permissões, proprietário. Em imagens, EXIF (câmera, data, GPS).
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_name = 'clientes';
Maceta: dicionário de dados = “o RG do banco”: diz quem é cada tabela e coluna.
Cai na prova assim:
  • “Os metadados ficam em arquivos externos ao SGBD, mantidos pelos programadores” → ERRADO. Ficam no catálogo do próprio SGBD.
  • “Metadados são os próprios dados operacionais do usuário” → ERRADO.
Resumo de 1 minutoMetadados = dados sobre dados. Ficam no dicionário/catálogo do SGBD, que garante a autodescrição. Information Schema é o padrão SQL para consultá-los.

Questões comentadas

Q1 (C/E): O catálogo de um SGBD armazena informações como estrutura de tabelas, tipos de dados e restrições.CERTO. É exatamente o conteúdo dos metadados.
Q2: A característica em que o SGBD guarda a descrição da própria estrutura é: a) Autodescrição b) Redundância c) Replicação d) ParticionamentoLetra a.

4. Modelagem Conceitual, Relacional e Normalização

Visão geral: um dos temas que mais cai. Aprenda o MER, as chaves e as formas normais.

Modelo Entidade-Relacionamento (MER)

  • Entidade: “coisa” do mundo real (Cliente, Pedido). Entidade fraca depende de outra para existir e não tem chave própria completa.
  • Atributos: simples, compostos (endereço = rua + cidade), multivalorados (vários telefones), derivados (idade, calculada da data de nascimento), identificador (chave).
  • Relacionamento e cardinalidade: 1:1, 1:N, N:N. Ex.: um Cliente faz muitos Pedidos (1:N).
  • Generalização/especialização: herança (Pessoa → Física, Jurídica).

Modelo relacional

TeoriaPrática
RelaçãoTabela

AtributoColuna

  • Chave candidata: identifica a linha de forma única e mínima. Primária (PK): a escolhida, não nula. Alternativa: candidata não escolhida. Estrangeira (FK): referencia a PK de outra tabela.
  • Integridade de entidade: PK nunca nula. Integridade referencial: toda FK aponta para um valor existente (ou é nula).
  • Mapeamento MER → tabelas: relação 1:N → FK no lado N. Relação N:N → nova tabela associativa com as duas chaves. Atributo multivalorado → tabela própria.

FNBC (Boyce-Codd)Todo determinante é chave candidata.
Maceta (Bill Kent): “Cada atributo depende da chave (1FN), da chave inteira (2FN) e nada além da chave (3FN).”

Exemplo 3FN: Pedido(id_pedido, id_cliente, nome_cliente). O nome_cliente depende de id_cliente, e não da chave do pedido: dependência transitiva. Solução: mover nome_cliente para a tabela Cliente.

Cai na prova assim:
  • “Uma tabela só com chave simples pode violar a 2FN” → ERRADO. Dependência parcial exige chave composta.
  • “Atributo multivalorado é permitido na 1FN” → ERRADO.
  • “O grau de uma relação é o número de tuplas” → ERRADO. É o de atributos.
Resumo de 1 minutoMER: entidade, atributo, relacionamento, cardinalidade. Relacional: tabela, linha, coluna, PK, FK. N:N vira tabela associativa. 1FN = atômico; 2FN = sem dependência parcial; 3FN = sem dependência transitiva.

Questões comentadas

Q1 (C/E): Um relacionamento N:N entre duas entidades é implementado no modelo relacional por meio de uma tabela associativa.CERTO. Ela recebe como FKs as chaves das duas entidades.
Q2: Uma tabela está na 2FN, mas um atributo comum depende de outro atributo comum. Ela viola a: a) 1FN b) 2FN c) 3FN d) integridade de entidadeLetra c. Isso é dependência transitiva.

Estrutura do SELECT

SELECT   departamento, COUNT(*) AS qtd
FROM     funcionarios
WHERE    ativo = 1
GROUP BY departamento
HAVING   COUNT(*) > 5
ORDER BY qtd DESC;
  • Ordem de execução: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.
  • WHERE filtra linhas antes de agrupar. HAVING filtra grupos (aceita funções agregadas).
  • Agregadas: COUNT, SUM, AVG, MIN, MAX. Ignoram NULL, exceto COUNT(*), que conta todas as linhas.
  • NULL é “desconhecido”: use IS NULL, nunca = NULL.
  • LIKE: % = qualquer sequência, _ = um caractere. BETWEEN é inclusivo. DISTINCT remove duplicatas.
  • UNION remove duplicados; UNION ALL mantém.

JOINs

DELETE x TRUNCATE x DROP

Cai na prova assim:

  • “TRUNCATE aceita cláusula WHERE” → ERRADO.
  • “WHERE nota = NULL retorna as linhas sem nota” → ERRADO. O correto é IS NULL.
  • “DROP TABLE remove apenas os registros” → ERRADO. Remove a tabela toda.

1. Big Data, NoSQL e Apache Hadoop

Visão geral: três peças que andam juntas: o problema (Big Data), o tipo de banco (NoSQL) e a ferramenta (Hadoop).

Big Data e os 5 Vs

Volume de dados tão grande, rápido e variado que bancos e ferramentas tradicionais não dão conta.

VSignificaExemplo
VolumeQuantidade enormePetabytes de logs
VelocidadeGeração e processamento rápidosStreaming de sensores
VariedadeFormatos diferentesTexto, vídeo, JSON
VeracidadeConfiabilidade e qualidadeDados com ruído ou erro
ValorUtilidade para o negócioInsight que gera decisão

Os 3 primeiros (Volume, Velocidade, Variedade) são os “3 Vs” clássicos.

NoSQL (“Not Only SQL”)

Bancos não relacionais, com esquema flexível e feitos para escala horizontal (adicionar mais servidores, e não um servidor maior, que é a escala vertical).

TipoIdeiaExemplos
Chave-valorUm “dicionário”: chave → valorRedis, DynamoDB
DocumentoGuarda documentos JSON/BSONMongoDB, CouchDB
Colunar (família de colunas)Dados por coluna, ótimo para grandes volumesCassandra, HBase
GrafoNós e arestas (relações)Neo4j
  • Chave-valor = cache, sessão. Grafo = redes sociais e recomendações.
  • ACID (relacional) x BASE (NoSQL): Basically Available, Soft state, Eventually consistent (consistência eventual).

Teorema CAP (Eric Brewer)

Em um sistema distribuído, só dá para garantir no máximo 2 de 3: Consistência, Availability (disponibilidade) e Partition tolerance (tolerância a partições de rede). Como falhas de rede acontecem, na prática escolhe-se entre CP ou AP.

Apache Hadoop

Plataforma open source para armazenar e processar grandes volumes de dados de forma distribuída, em um cluster de máquinas comuns (commodity hardware). Ideia-chave: levar o processamento até onde o dado está.

  • HDFS: sistema de arquivos distribuído. NameNode (mestre) guarda os metadados; DataNodes (escravos) guardam os blocos. Os blocos são replicados (padrão: 3 cópias) para tolerar falhas.
  • MapReduce: modelo de processamento em duas fases: Map (divide e transforma) → Reduce (agrega os resultados).
  • YARN: gerenciador de recursos e agendador de tarefas do cluster.
  • Ecossistema: Hive (consultas tipo SQL), HBase (banco colunar), Spark (processamento em memória, bem mais rápido que o MapReduce em disco).
Maceta: NameNode = “o bibliotecário” (sabe onde cada livro está); DataNodes = “as estantes” (guardam os livros). Se o bibliotecário cai, ninguém acha nada.
Cai na prova assim:
  • “O NameNode armazena os blocos de dados” → ERRADO. Guarda metadados; blocos ficam nos DataNodes.
  • “NoSQL não permite escalar horizontalmente” → ERRADO.
  • “O CAP permite garantir simultaneamente C, A e P” → ERRADO. No máximo duas.
  • “O Hadoop exige servidores de alto desempenho e custo elevado” → ERRADO. Foi pensado para hardware comum.
Resumo de 1 minutoBig Data = 5 Vs. NoSQL: chave-valor, documento, colunar, grafo; escala horizontal; BASE. CAP: no máximo 2 de 3. Hadoop = HDFS (NameNode metadados, DataNodes blocos, replicação) + MapReduce + YARN. Spark processa em memória.

2. Estruturação dos Dados

Visão geral: pergunta clássica: “este dado é estruturado, semi ou não estruturado?” e “o que fazer para deixá-lo pronto para análise?”.

TipoCaracterísticaExemplos
EstruturadoEsquema rígido, tabelas com linhas e colunas tipadasBancos relacionais, planilhas
SemiestruturadoSem tabela fixa, mas com marcadores/tags que descrevem o conteúdoJSON, XML, YAML, HTML
Não estruturadoSem organização interna predefinidaVídeo, áudio, imagem, PDF, e-mail, posts

A maior parte dos dados gerados hoje é não estruturada.

Formatos comuns

  • CSV: texto com valores separados por vírgula ou ponto e vírgula (parece tabela, mas sem tipos).
  • JSON: pares chave-valor, leve, muito usado em APIs.
  • XML: tags hierárquicas, pode ser validado por XSD; mais verboso.
  • YAML: legível por humanos, usa indentação (muito usado em configuração, como o Kubernetes).

Schema-on-write x Schema-on-read

  • Schema-on-write (banco relacional, DW): define a estrutura antes de gravar.
  • Schema-on-read (Data Lake): guarda o dado bruto e aplica a estrutura na hora de ler. O Data Lake aceita qualquer tipo; o DW, só dados tratados.

Pré-processamento (preparar para análise)

EtapaO que faz
LimpezaTrata valores ausentes (remover ou imputar), duplicados, outliers e inconsistências
IntegraçãoJunta dados de várias fontes
TransformaçãoConverte formatos, codifica categorias, escala valores
ReduçãoDiminui volume ou número de variáveis
  • Escalonamento: min-max (leva valores para 0–1) e padronização/z-score (média 0, desvio 1).
  • Qualidade de dados: completude, consistência, acurácia (precisão), atualidade e unicidade.
  • Outlier: valor muito fora do padrão (pode ser erro ou exceção real).
Cai na prova assim:
  • “JSON e XML são dados estruturados, pois têm tags” → ERRADO. São semiestruturados.
  • “Dados não estruturados não podem ser analisados” → ERRADO. Exigem técnicas específicas (texto, imagem).
  • Cuidado: “normalização” em análise de dados é escalar valores. Em banco de dados é 1FN, 2FN, 3FN. São coisas diferentes.
Resumo de 1 minutoEstruturado = tabela rígida. Semiestruturado = tags (JSON, XML, YAML). Não estruturado = vídeo, imagem, texto livre. DW = schema-on-write; Data Lake = schema-on-read. Pré-processamento: limpeza, integração, transformação, redução.

Questões comentadas

3. Inteligência Artificial (IA)

Visão geral: a banca cobra a diferença entre IA, ML e DL e os tipos de aprendizado.

Analogia (bonecas russas): a IA é a boneca maior; dentro dela está o Machine Learning; dentro dele, o Deep Learning.

  • IA: sistemas que simulam capacidades humanas (raciocinar, aprender, perceber, decidir).
  • Machine Learning (ML): o sistema aprende com dados, sem ser programado regra por regra.

Tipos de aprendizado

Maceta: Supervisionado = “aluno com gabarito”. Não supervisionado = “aluno sem gabarito, agrupa por semelhança”. Reforço = “cachorro que ganha petisco”.

Deep Learning e aplicações

  • CNN (redes convolucionais): imagens e visão computacional.
  • RNN/LSTM: sequências (texto, séries temporais).
  • Transformers: base dos modelos de linguagem atuais (LLMs, como o GPT) e da IA generativa, que cria texto, imagem e código.
  • PLN (Processamento de Linguagem Natural): entender e gerar linguagem humana. Visão computacional: interpretar imagens.
  • Modelos generativos podem sofrer alucinação (resposta convincente, porém errada), por isso exigem verificação humana.

Qualidade do modelo

  • Dados divididos em treino, validação e teste.
  • Overfitting: decorou o treino e vai mal em dados novos. Underfitting: não aprendeu nem o treino.
  • Métricas: acurácia (acertos totais), precisão (dos que previu positivos, quantos eram), recall (dos positivos reais, quantos achou), F1 (equilíbrio entre precisão e recall).
  • Viés: dados enviesados geram decisões injustas, e por isso falam-se em ética e transparência em IA.
Cai na prova assim:
  • “Clusterização é aprendizado supervisionado” → ERRADO. É não supervisionado.
  • “Regressão prevê categorias, como ‘aprovado’ ou ‘reprovado’” → ERRADO. Isso é classificação.
  • “Deep Learning e Machine Learning são áreas totalmente separadas” → ERRADO. DL é um subconjunto de ML.
  • “Overfitting é quando o modelo tem baixo desempenho nos dados de treino” → ERRADO. No overfitting, o desempenho no treino é bom.
Resumo de 1 minutoIA ⊃ ML ⊃ DL. Supervisionado = rótulos (classificação, regressão). Não supervisionado = sem rótulos (K-Means, PCA). Reforço = recompensa. DL = redes neurais profundas; CNN para imagens; Transformers para linguagem. Overfitting = decorou o treino.

7. Conceitos Fundamentais de Programação Web

Visão geral: como navegador e servidor conversam. É a base de segurança web e de APIs.

1. Java SE (Standard Edition)

Visão geral: Java é orientada a objetos, de tipagem estática e forte, e independente de plataforma (Write Once, Run Anywhere): o código-fonte .java é compilado para bytecode (.class), que roda em qualquer sistema com uma JVM.

SiglaO que é

Maceta: JDK ⊃ JRE ⊃ JVM (“bonecas russas”, do maior para o menor).

5. Frameworks Java · Spring Fundamentos

Visão geral: o Spring gira em torno de três ideias: IoC, DI e AOP.

Visão geral: o ORM (Mapeamento Objeto-Relacional) liga classes a tabelas, objetos a linhas e atributos a colunas, para você não escrever SQL em tudo.

3. Conceitos Básicos de Engenharia de Software

Visão geral: aplicar uma abordagem sistemática, disciplinada e quantificável ao desenvolvimento, operação e manutenção de software. O termo nasceu na crise do software (conferência da OTAN, 1968): projetos atrasados, caros e com baixa qualidade.

  • Atividades fundamentais: especificação, desenvolvimento (projeto e implementação), validação e evolução.
  • Verificação: “estamos construindo o produto corretamente?” (conforme a especificação). Validação: “estamos construindo o produto certo?” (atende à necessidade do cliente).
  • Gerência de configuração: controla versões e mudanças. Gerência de projeto: prazo, custo, escopo, riscos.

  • ISO/IEC 25010 (modelo de qualidade do produto), versão 2011: adequação funcional, eficiência de desempenho, compatibilidade, usabilidade, confiabilidade, segurança, manutenibilidade e portabilidade. Processo (as 4 grandes etapas)

  • “Os requisitos são levantados uma só vez, no início do projeto” → ERRADO. Mudam e são gerenciados.

6. Testes de Software

Visão geral: testar é executar o software para encontrar defeitos. Testes não provam a ausência de defeitos.

  • Erro (engano humano) → defeito (bug no código) → falha (comportamento errado observado em execução).

Níveis de teste

NívelFoco
UnidadeMenor parte (função, classe). Feito pelo desenvolvedor (JUnit)
IntegraçãoInteração entre módulos
SistemaO sistema completo, contra os requisitos
AceitaçãoO cliente valida. Alfa (no ambiente do desenvolvedor) e Beta (usuários reais, ambiente real)

Técnicas

  • Caixa-preta (funcional): testa entradas e saídas, sem ver o código. Partição de equivalência, análise do valor limite, tabela de decisão.
  • Caixa-branca (estrutural): usa o código. Cobertura de comandos, decisões (ramos) e caminhos. Complexidade ciclomática (McCabe): V(G) = E − N + 2 (arestas, nós) ou nº de decisões + 1; indica o número mínimo de caminhos independentes.
  • Exemplo de valor limite: campo aceita idade de 18 a 65. Testar 17, 18, 19, 64, 65 e 66.

Outros conceitos

  • Regressão: reexecutar testes após uma mudança, para ver se nada quebrou. Fumaça (smoke): teste rápido para ver se o build “liga”.
  • Desempenho: carga (uso esperado), estresse (além do limite). Ferramenta: JMeter.
  • Integração: top-down, bottom-up, big bang, sanduíche. Stub simula o módulo chamado; driver simula o módulo chamador.
  • TDD: ciclo Red (escreve teste que falha) → Green (código mínimo para passar) → Refactor (melhora). Mock simula dependências (Mockito). Selenium automatiza testes de interface web.
Cai na prova assim:
  • “Testes bem-sucedidos provam que não há defeitos” → ERRADO.
  • “Teste de caixa-preta exige conhecer o código-fonte” → ERRADO. Isso é caixa-branca.
  • “O driver simula o módulo chamado” → ERRADO. Isso é o stub.
Resumo de 1 minutoNíveis: unidade, integração, sistema, aceitação (alfa/beta). Caixa-preta = sem código; caixa-branca = com código (cobertura, McCabe). Regressão após mudança. Stub = chamado; driver = chamador. TDD: Red, Green, Refactor.

Arquitetura e Organização de Computadores

Visão geral: “Arquitetura” é o que o programador enxerga (conjunto de instruções, registradores). “Organização” é como isso é construído no hardware (barramentos, circuitos).

1. Modelo de Von Neumann

  • Três blocos ligados por barramentos: CPU (UC + ULA + registradores), memória principal e E/S.
  • Ideia central: programa armazenado. Instruções e dados ficam na mesma memória.
  • Gargalo de Von Neumann: como instruções e dados disputam o mesmo caminho até a memória, o acesso limita o desempenho.
  • Arquitetura Harvard: memórias e barramentos separados para instruções e dados. As caches L1 modernas usam essa ideia (Harvard modificada).

2. A CPU por dentro

ComponenteFunção
UC (Unidade de Controle)Busca e decodifica instruções e comanda os demais componentes
ULA (Unidade Lógica e Aritmética)Executa operações aritméticas e lógicas
RegistradoresMemória mais rápida, dentro da CPU
  • PC (contador de programa): endereço da próxima instrução. IR: instrução em execução. MAR: endereço a acessar. MBR/MDR: dado lido ou a escrever. ACC: acumulador. Flags/PSW: status (zero, overflow, carry).
  • Ciclo de instrução: busca (fetch) → decodificação → execução → (escrita do resultado). Depois verifica-se se há interrupção.
BarramentoSentidoDetalhe
DadosBidirecionalA largura define quantos bits trafegam por vez

3. Hierarquia de memória

Regra de ouro: quanto mais perto da CPU, mais rápida, mais cara, menor e mais volátil. Ordem: Registradores → Cache (L1, L2, L3) → RAM → SSD/HD.
  • Por que funciona? Princípio da localidade: temporal (o que foi usado será usado de novo logo) e espacial (vizinhos do que foi usado serão usados).
  • Cache hit = achou na cache; miss = foi buscar na RAM.
  • Mapeamento da cache: direto (cada bloco tem uma única linha possível; simples, mais conflitos), totalmente associativo (qualquer linha; flexível, caro) e associativo por conjunto (meio-termo, o mais usado). Substituição: LRU (menos recentemente usado), FIFO, aleatória.
  • Escrita: write-through grava na cache e na RAM juntas; write-back grava só na cache e atualiza a RAM depois (usa dirty bit).
TipoCaracterísticaUso
SRAMRápida, cara, não precisa de refreshCache
DRAMCapacitores, precisa de refresh, mais barata e densa (DDR)Memória principal
ROM e derivadasNão volátil. PROM (grava 1 vez), EPROM (apaga com luz UV), EEPROM (apaga eletricamente), Flash (EEPROM por blocos)Firmware/BIOS, SSD, pen drive

RAM = volátil (perde o conteúdo sem energia). SSD/HD = armazenamento secundário, não volátil.

4. Pipeline de instruções

Analogia: lavanderia com várias etapas (lavar, secar, passar): enquanto uma roupa seca, outra já lava. As etapas se sobrepõem.

  • Estágios típicos: busca → decodificação → execução → acesso à memória → escrita.
  • O pipeline aumenta a vazão (instruções concluídas por tempo), mas não reduz o tempo de uma instrução isolada.
  • Hazards (conflitos): estrutural (dois estágios querem o mesmo recurso), de dados (instrução depende do resultado de outra) e de controle (desvios/saltos). Soluções: forwarding, stall (bolha) e predição de desvio.
  • Superescalar: vários pipelines, mais de uma instrução por ciclo.

7. Paralelismo e desempenho

  • Taxonomia de Flynn: SISD (um fluxo de instrução e um de dados: CPU sequencial clássica) · SIMD (uma instrução sobre vários dados: GPU, instruções vetoriais) · MISD (raro) · MIMD (vários fluxos independentes: multiprocessadores, multicore).
  • Multicore: vários núcleos no mesmo chip. Hyper-Threading/SMT: um núcleo executa duas threads ao mesmo tempo, aproveitando ociosidade.
  • Tempo de CPU = (nº de instruções × CPI) ÷ frequência de clock. CPI = ciclos por instrução. Clock mede-se em Hz (GHz).
  • Lei de Amdahl: o ganho por paralelizar é limitado pela parte sequencial do programa. Speedup = 1 ÷ [(1 − p) + p/n], com p = fração paralelizável e n = nº de processadores.

8. Representação de dados

  • Bases: binária (2), octal (8), hexadecimal (16). 1 dígito hexa = 4 bits; 1 dígito octal = 3 bits. Ex.: 0xA3 = 1010 0011 = 163.
  • Complemento de dois (inteiros com sinal): para negativar, inverta os bits e some 1. Faixa com n bits: −2ⁿ⁻¹ a 2ⁿ⁻¹−1 (8 bits: −128 a 127).
  • Ponto flutuante IEEE 754: simples = 32 bits (1 sinal + 8 expoente + 23 mantissa); dupla = 64 bits (1 + 11 + 52).
  • Caracteres: ASCII usa 7 bits (128 símbolos). Unicode cobre todos os idiomas; UTF-8 usa 1 a 4 bytes por caractere e é compatível com ASCII.
  • Unidades: 1 byte = 8 bits. No uso tradicional, 1 KB = 1024 bytes (o padrão IEC chama de KiB; kB = 1000 no SI).

Programação Estruturada e POO

Visão geral: primeiro você aprende a organizar o raciocínio em estruturas simples (estruturada); depois, a modelar o problema como objetos que colaboram entre si (POO).

1. Base: algoritmos e lógica

  • Algoritmo: sequência finita e ordenada de passos que resolve um problema. Representações: pseudocódigo (portugol), fluxograma (símbolos gráficos) e linguagem de programação.
  • Variável: espaço de memória com nome, cujo valor pode mudar. Constante: valor fixo. Tipos primitivos: inteiro, real, caractere, lógico (booleano).
  • Operadores: aritméticos (+ − * /, % resto), relacionais (== != < >) e lógicos (E/AND, OU/OR, NÃO/NOT).
  • Precedência: parênteses → NÃO → multiplicação/divisão → soma/subtração → relacionais → E → OU.
  • Atribuição (= ou <-) grava um valor; comparação (==) testa igualdade.
  • Tradutores: compilador converte todo o código antes da execução (Java, C); interpretador executa linha a linha (Python, JavaScript); assembler traduz assembly.

2. Programação estruturada

Todo programa pode ser escrito com apenas 3 estruturas (teorema de Böhm-Jacopini), sem o desvio incondicional goto:

EstruturaExemplos
SequênciaComandos executados um após o outro
Seleção (decisão)if / else, switch/case
Repetição (laço)while (testa antes; pode não executar nenhuma vez), do-while (testa depois; executa ao menos 1 vez), for (quantidade conhecida)
  • Modularização: dividir o programa em funções (devolvem valor) e procedimentos (não devolvem). Vantagens: reuso, legibilidade, manutenção. Projeto top-down: do geral ao detalhe.
  • Escopo: variável local existe só dentro da função; global é visível em todo o programa (usar com cuidado).
  • Passagem de parâmetros: por valor (recebe uma cópia; a original não muda) x por referência (recebe o endereço; a original pode mudar).
  • Recursão: função que chama a si mesma. Exige caso base (condição de parada), senão estoura a pilha (stack overflow).

   retorne n * fatorial(n - 1)   // chamada recursiva

1. BPM (Gerenciamento de Processos de Negócio)

Visão geral: BPM é uma disciplina de gestão que enxerga a organização como um conjunto de processos e busca melhorá-los continuamente.

  • Processo: conjunto de atividades inter-relacionadas que transformam entradas em saídas, gerando valor para o cliente.
  • Visão por processos (horizontal, ponta a ponta) x visão funcional (vertical, por departamentos). O BPM atravessa os departamentos.
  • Tipos de processo (CBOK): primários/finalísticos (entregam valor direto ao cliente), de suporte (apoiam os primários, ex.: RH, TI) e de gerenciamento (planejam e controlam).
  • AS-IS = como o processo é hoje. TO-BE = como será após a melhoria.

Ciclo de vida do BPM

Planejamento → Análise (AS-IS) → Desenho (TO-BE) → Implementação → Monitoramento e controle → Refinamento (e volta ao início). É um ciclo contínuo, parecido com o PDCA.

  • Indicadores (KPIs): medem o desempenho (tempo de ciclo, custo, retrabalho, satisfação).
  • BPMS: software para modelar, executar e monitorar processos (workflow). RPA: robôs que automatizam tarefas repetitivas.
  • Melhoria: Lean (elimina desperdícios) e Six Sigma (reduz variação; ciclo DMAIC: Definir, Medir, Analisar, Melhorar, Controlar).
  • Dono do processo: responsável pelo desempenho do processo de ponta a ponta. ABPMP publica o guia BPM CBOK.
Cai na prova assim:
  • “BPM é sinônimo de automação de processos por software” → ERRADO. Automação é só uma parte; BPM é gestão.
  • “O modelo AS-IS representa o processo futuro desejado” → ERRADO. Isso é TO-BE.
Resumo de 1 minutoProcesso = entradas → saídas com valor. Primário, suporte, gerenciamento. Ciclo: planejar, analisar (AS-IS), desenhar (TO-BE), implementar, monitorar, refinar. BPMS automatiza; Lean/Six Sigma melhoram.

Q2: O processo que entrega valor diretamente ao cliente externo é: a) de suporte b) de gerenciamento c) primário d) de melhoriaLetra c.

1. Conceitos Básicos e Topologias de Redes

  • Alcance: PAN (pessoal), LAN (local, um prédio), MAN (metropolitana), WAN (extensa, países; a Internet é a maior).
  • Sentido da transmissão: simplex (só um sentido: TV), half-duplex (nos dois sentidos, mas um de cada vez: rádio) e full-duplex (simultâneo: telefone).

  • Desempenho: largura de banda (capacidade), latência (atraso), jitter (variação do atraso), vazão/throughput (taxa real).

5. LAN, VLAN, MPLS, Roteamento e Redes Sem Fio

LAN e VLAN

  • O switch aprende os MACs na sua tabela. Destino desconhecido ou broadcast → flooding (envia por todas as portas).
  • STP (IEEE 802.1D) evita loops bloqueando portas redundantes; RSTP (802.1w) converge mais rápido. LACP (802.3ad) agrega links.
  • VLAN (IEEE 802.1Q): divide logicamente um switch em redes separadas, cada VLAN = um domínio de broadcast. Tag de 4 bytes com ID de 12 bits (até 4094 VLANs). Porta access (uma VLAN) x porta trunk (várias VLANs com tag). Para comunicar entre VLANs, é preciso roteamento (roteador ou switch camada 3).

Funções hash

  • Entrada qualquer → saída de tamanho fixo (resumo). Unidirecional (não se reverte) e com efeito avalanche (1 bit muda tudo). Uso: integridade e armazenamento de senhas (com salt).
  • MD5 (128 bits) e SHA-1 (160 bits): quebrados/obsoletos. SHA-2 (SHA-256, SHA-512) e SHA-3: seguros. Hash não é criptografia (não há chave nem volta).

PKI e ICP-Brasil

  • Certificado digital (X.509): documento eletrônico que liga uma chave pública a uma identidade, assinado por uma Autoridade Certificadora (AC). Traz titular, chave pública, validade, assinante e número de série. LCR/OCSP informam certificados revogados.
  • Cadeia de confiança: AC Raiz → ACs intermediárias → certificados finais. AR (Autoridade de Registro) valida a identidade do solicitante, mas não emite.
  • ICP-Brasil: infraestrutura oficial de chaves públicas, criada pela MP 2.200-2/2001. A AC Raiz é o ITI (Instituto Nacional de Tecnologia da Informação). Dá validade jurídica a documentos eletrônicos assinados.
  • Tipos: A1 (chave no software, validade curta) e A3 (chave em hardware: token ou cartão). Há também S (sigilo) e T (carimbo do tempo).

Conceitos Básicos, Processos, Memória e Arquivos

1. Visão geral do SO

O SO é a camada entre o hardware e os programas: gerencia recursos (CPU, memória, disco, dispositivos) e oferece uma interface ao usuário. Duas visões: máquina estendida (esconde a complexidade do hardware) e gerente de recursos (divide recursos entre programas).

  • Modo usuário x modo kernel: o kernel roda com privilégios totais; programas comuns, restritos. Para pedir um serviço ao kernel, o programa faz uma chamada de sistema (system call). Interrupção: sinal que desvia a CPU para tratar um evento (E/S, timer).
Arquitetura do kernelIdeia
MonolíticoQuase tudo no espaço do kernel; rápido, mas uma falha pode derrubar tudo (Linux)
MicrokernelSó o essencial no kernel; serviços em espaço de usuário. Mais estável e seguro, porém mais lento (comunicação entre módulos)
HíbridoMistura dos dois (Windows NT, macOS)
  • Tipos de SO: em lote (batch), tempo compartilhado (multitarefa), tempo real (prazos garantidos: hard e soft), distribuído, embarcado.
  • Boot: firmware (BIOS/UEFI) → gerenciador de boot (GRUB) → kernel → processo inicial (init/systemd).
  • Multiprogramação (vários programas na memória) ≠ multiprocessamento (várias CPUs) ≠ multitarefa (alternância rápida que dá ilusão de simultaneidade).

2. Processos e threads ★★★

  • Programa é passivo (arquivo no disco); processo é o programa em execução, com seu espaço de endereçamento, registradores e recursos. O SO guarda tudo no PCB (Bloco de Controle de Processo).
  • Troca de contexto: salvar o estado de um processo e carregar o de outro. É custo puro (overhead).
Estados e transições: Novo → Pronto ⇄ Executando → Terminado; de Executando vai a Bloqueado (espera E/S) e daí volta a Pronto (nunca direto a Executando).
  • Pronto → Executando: despacho (escolhido pelo escalonador).
  • Executando → Pronto: preempção (acabou o quantum).
  • Executando → Bloqueado: pediu E/S ou recurso.
  • Bloqueado → Pronto: a E/S terminou.

3. Escalonamento de CPU ★★★

O escalonador decide qual processo pronto usa a CPU. Não preemptivo: o processo só sai ao terminar ou bloquear. Preemptivo: o SO pode tirar a CPU dele.

4. Sincronização e deadlock ★★★

  • Condição de corrida: o resultado depende da ordem de execução de processos/threads que acessam o mesmo dado. Seção crítica: trecho que acessa recurso compartilhado e exige exclusão mútua.
  • Mecanismos: semáforo (Dijkstra; operações P/wait e V/signal), mutex (semáforo binário), monitor. Problemas clássicos: produtor-consumidor, leitores-escritores, jantar dos filósofos.

Deadlock (impasse)

Processos esperando uns pelos outros indefinidamente. Ocorre somente se as 4 condições de Coffman ocorrerem juntas:

1. Exclusão mútuaO recurso só pode ser usado por um processo por vez
2. Posse e esperaSegura um recurso enquanto espera outro
3. Não preempçãoO recurso não pode ser tomado à força
4. Espera circularCiclo de processos, cada um esperando o recurso do próximo
  • Tratamento: prevenção (eliminar uma das 4 condições), evitação (algoritmo do banqueiro, que só concede se o estado for seguro), detecção e recuperação e ignorar (“algoritmo do avestruz”, comum em Unix e Windows).
  • Deadlock x inanição (starvation): no deadlock ninguém avança; na inanição, um processo nunca é atendido, mas os demais seguem.

Memória virtual

  • Permite executar programas maiores que a RAM, mantendo na memória só as páginas em uso; o resto fica no disco (swap). Baseia-se no princípio da localidade.
  • Falta de página (page fault): a página acessada não está na RAM. O SO a carrega do disco, e se não houver quadro livre, substitui uma página.
